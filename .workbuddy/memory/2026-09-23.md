## Redis 超时告警分析（StackExchange.Redis.RedisTimeoutException）
- 现象：GroupControlService / RedisCmdWorker / MqttMessageWorker(AgingDataHandler) 同时报 5000ms 超时，outbound=0KiB inbound=0KiB，最后升级为 ConnectTimeout。
- 结论：Redis 服务端 192.168.1.65:6379 当时不可达或单线程被阻塞，不是业务代码 bug；三个组件共用 Program.cs 注册的单例 IConnectionMultiplexer（未配置 syncTimeout/connectTimeout，用默认 5s），一个阻塞全部超时。
- 代码隐患：MarkSeenAsync 每次 4 次串行往返（HGETALL+SADD+ZADD+HMSET），高频 data/aging 是主要写入源；MqttMessageWorker 单条串行 await 造成拥塞放大；GroupControlService 1s 轮询每架多次往返（SMEMBERS/LRANGE 为 O(N)）；无熔断/背压；未订阅 ConnectionFailed/Restored 事件日志。

## 群控流程梳理（源码级结论）
- 隔离粒度：按 AgingNumber 全隔离。状态 `lgw:group-control:{n}:state`、批次 `...:run:{RunSeq}:{state|participants|started|completed|terminal}`、成员 `lgw:devices:online:aging:{n}`、锁 `_rackLocks[n]`。架注册表 `lgw:group-control:racks`（SaveStateAsync 自动 SADD）。
- 架间并行：`ExecuteAsync` 每 1s `GetRackNumbersAsync` 后 `Task.WhenAll(ProcessRackAsync)`，各架持各锁；架内串行。
- 流程：up_line 归属 → deviceMode Mode=2(Generation++) → start_aging 登记候选(Candidate) → 设备真实 agingStart 才激活(ActivateRunUnsafeAsync，已有批次则 Conflict 拒绝) → TaskCP 屏障(participants.All(completed)，与在线列表无关) → 广播 `server/public/Cannextstep` → 终态全员 → Finished。
- 控电：agingStage → CPower 定向本架唯一在线总控（0 个或多个总控则保留 pending 不下发）；Recharge=1，其余=0。
- 跨架泄漏点（设计风险）：`server/public/Cannextstep` 是公共主题且 payload 无 AgingNumber，两架同时 Mode=2 时会互相收到对方的放行广播；deviceMode/agingStage 同为公共主题，仅靠 Data.AgingNumber 区分。
- 总控在线列表是全局 `lgw:devices:online:control`，靠元素内 AgingNumber 过滤（ParseDeviceIds），点位才是按架分 List。

## 放行主题改按架隔离（方案阶段，代码未改）
- 用户诉求：`server/public/Cannextstep` → 按 AgingNumber 分主题。唯一代码出口 `GroupControlService.cs:961`（`TryPublishNextStepUnsafeAsync`，该方法已接收 agingNumber 参数，目前只用于日志）。
- 建议命名：`server/rack/{AgingNumber}/Cannextstep`（推荐）/ 最规范 `server/rack/{n}/cmd/Cannextstep`；不推荐 `server/{n}/Cannextstep`（与 `server/{deviceId}/cmd/{action}` 同层，语义二义）。
- 关键事实：服务侧只发布不订阅，`MqttConnection.SubscribeAllTopicsAsync` 无需改动；pending 序列化（PendingGroupControlCommand{Seq,Stage,Payload}）不含 topic，改主题无需清 Redis、无数据迁移；publish QoS=AtLeastOnce、无 retain。
- 校验：`RedisKeys.NormalizeAgingNumber`（纯数字、非负 int、去前导零），校验失败应保留 pending 并告警，绝不退化成 public 广播。
- 兼容：设备端仍订阅 public 会导致收不到放行 → 群控卡死在阶段边界，必须双写或固件同步升级。
