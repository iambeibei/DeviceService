# 2026-09-28

## 全项目代码梳理（设备放行 / 老化架隔离 / 端到端流程）

通读 DeviceService 与 Bluetti.Device.Redis 全部源码，输出结论性总结。核心结论：

- 放行分三层：① 命令队列级（同设备串行，回复或超时才放行下一条，RedisCmdWorker.ProcessDeviceQueueAsync）；
  ② start_aging 门控级（AgingCommandGate，仅 agingIdle/agingStop/agingError 释放，failed 释放、timed_out 不释放）；
  ③ 群控批次级（GroupControlService.EvaluateNextStepUnsafeAsync，participants 全部 TaskCP 完成才发
  server/rack/{AgingNumber}/CanNextstep，payload {Seq, Data:{IsCanNext:1}}）。
- 老化架唯一标识是字符串 AgingNumber（非负整数），经 RedisKeys.NormalizeAgingNumber 规范化；
  隔离维度：lgw:devices:online:aging:{n}、lgw:group-control:{n}:*、MQTT 主题 server/rack/{n}/CanNextstep、
  server/{controllerId}/cmd/CPower（定向到该架唯一在线 type=2 总控）。
- 群控批次 RunSeq 复用 Redis Stream 的 start_aging Seq；批次状态 candidate/active/finished/conflict/cancelled；
  只有设备真实上报 agingStart 才激活候选批次，timed_out 不算激活。
- 端到端：平台写 lgw:cmd:queue(字段 data) → RedisCmdWorker 展 DeviceInfos → 按设备队列 → MQTT
  server/{id}/cmd/{action} → 设备回复 device/{id}/cmd/reply/{type} → CompleteAsync 唤醒 → XACK。
- 关键陷阱：published 不等于已发送（重启用原 Seq 重发，设备端需按 Seq 幂等）；
  CanNextstep 绝不能退化成公共广播；CPower 需该架恰好 1 个在线总控。

未改动任何代码，纯分析。

### 补充澄清：放行判定的集合口径

阶段放行判定用的是 `...run:{runSeq}:participants`（批次登记时固化的候选集合，来自批量 start_aging
的 DeviceInfos），**不是**"实际上报过 agingStart 的设备集合"：

- `participants`：RegisterAgingBatchAsync 按 (AgingNumber, Seq) 登记，激活后固化，判定依据。
- `started`（`...run:{runSeq}:started`）：只有 AddRunStartedDeviceAsync，**全代码无读取方法**，纯审计，
  不参与任何判定。
- `completed`：TaskCP(IsComplete=1) 集合，放行成功后 ClearRunCompletedDevicesAsync 清空，按阶段重新收集。
- `terminal`：agingIdle/Stop/Error 集合，只用于批次 finished 判定。

判定式：canRelease = participants.Count > 0 && participants.All(completed.Contains)（GroupControlService.cs:906）。
差异影响：在 participants 但始终没上报 agingStart/掉线的设备会永久阻塞放行；上报了 agingStart 但不在
participants 的设备，其 TaskCP 被 RecordTaskCompletionAsync 丢弃（不阻塞也不放行）。

### 改造方案（已出计划，待确认，文档在 docs/群控阶段超时与TTL改造方案.md）

三项：① Redis TTL 统一到 RedisTtl 常量类（RedisHelper 多数写入方法当前根本不支持 TTL；
runtime / event:state / 在线列表 / group-control:racks 与 :state / cmd:seq 必须保持永久，否则
设备 AgingNumber 丢失会让运行中批次永不结束、Seq 回退）；② 阶段半数达成后 10 分钟超时，到期剔除
未完成设备出 participants + 写 event:fault + 放行（阈值 Ceil(n/2)，deadline 存 state，复用 1s 轮询
不引入 Timer，剔除者当前批次不再回归）；③ 放行指令回复校验，复用 CommandRepository.EnsureStored +
WaitForCompletionAsync（同一 Seq 可按设备各建 cmd Hash）。

两个阻塞点待用户确认：
- 放行回复报文是 Data.CmdSeq（现有协议）还是示例中的顶层 CmdSeq（现有 Handler 会丢弃后者）；
- SaveEventAsync 内部 MarkSeenAsync 会把离线设备标记 Online=true，写故障必须走新的不 MarkSeen 路径。

本次未改动任何业务代码（截至此处仅 TTL 部分已改）。

### 线路 A 已确认（放行回复协议）

设备收到 `server/rack/{n}/CanNextstep` 后，按现有协议回复：
主题 `device/{id}/cmd/reply/point`，报文 `{"Seq":..,"Data":{"CmdSeq":<放行Seq>,"Code":1,"Msg":null,"CmdData":null}}`。
→ 不需要改 CommandResponseHandler，现有 PointCommandReplyHandler 可直接接住；
→ 前提是发布前用 CommandRepository.EnsureStoredAsync 建好 lgw:device:{id}:cmd:{seq}。

最终计划已写入 docs/群控阶段超时与TTL改造方案.md 的 §7。两个关键实现坑：
1. WaitForCompletionAsync 遇终态立即返回，且 MarkPublished/MarkQueued 有终态保护 →
   重试前必须新增 ResetForRetryAsync 强制改回 published。
2. SaveEventAsync 会 MarkSeenAsync 把离线设备标记在线 → 故障必须走新的 SaveGroupControlFaultAsync。

### 用户收敛 TTL 范围 + Redis 过期机制澄清

有效期只针对三键：`lgw:device:{id}:aging:{pn}:history`、`lgw:device:{id}:cmd:{seq}`、`lgw:cmd:queue`。

Redis 过期机制：EXPIRE 到期不是精确时刻删除，而是「惰性删除（访问时判定）+ 主动抽样（hz=10 每秒抽样）」；
逻辑上过期即不可见，且**整键删除**（不是删 field、也不是按 Stream 元素裁剪）。

重大风险（已告知用户）：`lgw:cmd:queue` 设 TTL 后若长期空闲，key 连同消费者组 `device-service`
一起消失，而 `RedisCmdWorker.ExecuteAsync` 只在启动时 `EnsureGroupAsync()` 一次 → 之后
`StreamReadGroupAsync` 持续 NOGROUP 报错，命令通道永久卡死需重启，且未 ACK Pending 全丢。
推荐改为 `XTRIM MINID`（StackExchange.Redis 3.0.11 支持）按时间裁剪，key 与消费组保留。

③ 放行回复校验失败 **不用**联动剔除 participants。

- `CommandRepository.ResetForRetryAsync(deviceId, seq)`：强制改回 published + 清终态字段
  （因为 WaitForCompletionAsync 遇终态立即返回、MarkPublished 有终态保护，不重置重试就白等）。
- `DeviceRepository.SaveGroupControlFaultAsync(...)`：**不调用 MarkSeenAsync**，避免把离线设备复活成在线。

`GroupControlService` 核心改动：
- `EvaluateNextStepUnsafeAsync` 三段固定顺序：**先超时剔除 → 再判放行 → 最后按需起表**。
- `ExpireStageTimeoutUnsafeAsync`：participants \ completed → SREM participants + SADD excluded →
  （RaiseFaultOnStageTimeout）写 fault + publish event:fault → 清 StageDeadlineUtc + 记 LastStageTimeoutSeq。
  剔除设备本批次不回归，只能等下一个 RunSeq。
- `ComputeHalfThreshold`：`(int)Math.Ceiling(count/2.0)`（Floor 可用配置切）。
- `TryPublishNextStepUnsafeAsync`：发布前 `StoreReleaseCommandsAsync`（每台 participant
  `EnsureStoredAsync`，Action="can_next"、Seq=放行 Seq）；发布成功后 `StartReleaseVerification`。
- `VerifyReleaseRepliesAsync`：`Task.WhenAll` 并发 `WaitForCompletionAsync` →
  `completed && ResultCode==1` 判成功；否则 `MarkTimedOutAsync` → 整架重发（**原 Seq**）→

### 分析：设备自报终态 / 报 fault / 掉线 对群控的影响（未改代码）

结论：**三种异常都不会把设备移出 participants**，而放行判定是
`participants.All(completed.Contains)`（`GroupControlService.EvaluateNextStepUnsafeAsync`），
terminal 集合与在线状态**都不参与判定**，所以异常设备会一直被等待 TaskCP → 阻塞整架放行。

- 报 agingStop/agingError/agingIdle → `HandleAgingStateAsync` → `SADD ...run:{seq}:terminal`；
  participants 不变。terminal 只用于 `participants.All(terminal.Contains)` 判批次 finished。
  若该设备已报过 TaskCP（在 completed 里）则不影响放行；否则永久阻塞。
- 报 fault 事件 → `DeviceEventHandler` 只写 event:fault + publish，**完全不碰群控集合**，
  仍在 participants 中被等待。
- 掉线（device/public/down_line）→ `DeviceOfflineHandler` → `SaveOfflineAsync`（移出在线列表、
  Online=false）→ `ReevaluateMembershipAsync` 只触发一次 `ProcessRackAsync` 重估，
  **不改 participants、不加 terminal** → 永久阻塞。总控掉线另会卡住 CPower pending。

新加的 10 分钟超时只在"completed 已达 Ceil(半数)"时才起表，因此：
- 已达半数 → 10 分钟后剔除异常设备、放行剩余；
- **不足半数（如 5 台只完成 2 台）→ 永远不起表 → 批次永久挂起**，需人工干预。

命令层另有一处独立风险：`AgingCommandGate` 无超时兜底，设备掉线后 runtime 仍是 agingStart
→ 门永久 Reserved → 该设备后续所有 start_aging 永久排队（timed_out 不释放门）。

待用户决定是否补的兜底：① 终态/掉线即移出 participants（或计入免等待）；
② 倒计时改为"有未完成就起表"而非要求过半数；③ 放行校验跳过离线设备（当前会误报 fault）；
④ AgingCommandGate 加兜底超时。

→ 用户回复"按你建议直接修改"，四条**全部已实施**，编译 0 错误（6 警告均为既有）。
方案文档新增 §9「异常设备兜底」。

实施要点：
1. `GroupControlService.ExcludeParticipantUnsafeAsync(n, runSeq, deviceId, reason, message)`：
   SREM participants + SADD excluded + （RaiseFaultOnExclusion）写 fault + publish。
   reason 取值 `aging_terminal` / `device_offline` / `stage_timeout`。
2. `FinishRunUnsafeAsync(n, state, runSeq, reason)`：批次 finished + 清 CurrentRunSeq /
   PendingNextStep / StageDeadlineUtc / completed。原 finished 分支改为复用。
   **新增兜底**：EvaluateNextStepUnsafeAsync 里 participants.Count == 0 时直接结束批次
   （空集合下 All() 恒真但被 Count>0 挡住 → 既不放行也不结束 → 挂死）。
3. `HandleDeviceOfflineAsync(deviceId)`（新公开方法）由 `DeviceOfflineHandler` 在
   SaveOfflineAsync 之后、ReevaluateMembershipAsync 之前调用（先剔除再重估才会放行）。
4. `StageTimeoutRequireHalf`（默认 false）：有任意一台完成即起表，不再要求过半数。
5. `FilterOnlineParticipantsAsync`：放行校验前与每轮重试前都过滤离线设备；
   全离线时走 clearedByOffline 分支，不再误记"已收到全部确认"。
6. `AgingCommandGate`：`WaitAndReserveAsync` 改 `Task.WhenAny(stateChangedTask, Task.Delay(timeout))`；
   超时且**设备已离线**才强制开门（设备在线时老化可能数小时，不能按时间插队穿透）。
   配置 `AgingCommandGate:OfflineReleaseTimeoutMinutes` 默认 30。

被剔除设备本批次不回归（Rejoin 能力未做）。
