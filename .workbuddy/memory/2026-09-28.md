# 2026-09-28

## 全项目代码梳理（设备放行 / 老化架隔离 / 端到端流程）

通读 DeviceService 与 Bluetti.Device.Redis 全部源码，输出结论性总结。核心结论：

- 放行分三层：① 命令队列级（同设备串行，回复或超时才放行下一条，RedisCmdWorker.ProcessDeviceQueueAsync）；
  ② start_aging 门控级（AgingCommandGate，仅 agingIdle/agingStop/agingError 释放，failed 释放、timed_out 不释放）；
  ③ 群控批次级（GroupControlService.EvaluateNextStepUnsafeAsync，participants 全部 TaskCP 完成才发
  server/rack/{AgingNumber}/CanNextstep，payload {Seq, Data:{IsCanNext:1}}）。
- 老化架唯一标识是字符串 AgingNumber（非负整数），经 RedisKeys.NormalizeAgingNumber 规范化；
  隔离维度：lgw:devices:online:aging:{n}、lgw:group-control:{n}:*、MQTT 主题 server/rack/{n}/CanNextstep、
  server/{controllerId}/cmd/CPower（定向到该架唯一在线 type=2 总控）。
- 群控批次 RunSeq 复用 Redis Stream 的 start_aging Seq；批次状态 candidate/active/finished/conflict/cancelled；
  只有设备真实上报 agingStart 才激活候选批次，timed_out 不算激活。
- 端到端：平台写 lgw:cmd:queue(字段 data) → RedisCmdWorker 展 DeviceInfos → 按设备队列 → MQTT
  server/{id}/cmd/{action} → 设备回复 device/{id}/cmd/reply/{type} → CompleteAsync 唤醒 → XACK。
- 关键陷阱：published 不等于已发送（重启用原 Seq 重发，设备端需按 Seq 幂等）；
  CanNextstep 绝不能退化成公共广播；CPower 需该架恰好 1 个在线总控。

未改动任何代码，纯分析。

### 补充澄清：放行判定的集合口径

阶段放行判定用的是 `...run:{runSeq}:participants`（批次登记时固化的候选集合，来自批量 start_aging
的 DeviceInfos），**不是**"实际上报过 agingStart 的设备集合"：

- `participants`：RegisterAgingBatchAsync 按 (AgingNumber, Seq) 登记，激活后固化，判定依据。
- `started`（`...run:{runSeq}:started`）：只有 AddRunStartedDeviceAsync，**全代码无读取方法**，纯审计，
  不参与任何判定。
- `completed`：TaskCP(IsComplete=1) 集合，放行成功后 ClearRunCompletedDevicesAsync 清空，按阶段重新收集。
- `terminal`：agingIdle/Stop/Error 集合，只用于批次 finished 判定。

判定式：canRelease = participants.Count > 0 && participants.All(completed.Contains)（GroupControlService.cs:906）。
差异影响：在 participants 但始终没上报 agingStart/掉线的设备会永久阻塞放行；上报了 agingStart 但不在
participants 的设备，其 TaskCP 被 RecordTaskCompletionAsync 丢弃（不阻塞也不放行）。

### 改造方案（已出计划，待确认，文档在 docs/群控阶段超时与TTL改造方案.md）

三项：① Redis TTL 统一到 RedisTtl 常量类（RedisHelper 多数写入方法当前根本不支持 TTL；
runtime / event:state / 在线列表 / group-control:racks 与 :state / cmd:seq 必须保持永久，否则
设备 AgingNumber 丢失会让运行中批次永不结束、Seq 回退）；② 阶段半数达成后 10 分钟超时，到期剔除
未完成设备出 participants + 写 event:fault + 放行（阈值 Ceil(n/2)，deadline 存 state，复用 1s 轮询
不引入 Timer，剔除者当前批次不再回归）；③ 放行指令回复校验，复用 CommandRepository.EnsureStored +
WaitForCompletionAsync（同一 Seq 可按设备各建 cmd Hash）。

两个阻塞点待用户确认：
- 放行回复报文是 Data.CmdSeq（现有协议）还是示例中的顶层 CmdSeq（现有 Handler 会丢弃后者）；
- SaveEventAsync 内部 MarkSeenAsync 会把离线设备标记 Online=true，写故障必须走新的不 MarkSeen 路径。

本次未改动任何业务代码。

### 用户收敛 TTL 范围 + Redis 过期机制澄清

有效期只针对三键：`lgw:device:{id}:aging:{pn}:history`、`lgw:device:{id}:cmd:{seq}`、`lgw:cmd:queue`。

Redis 过期机制：EXPIRE 到期不是精确时刻删除，而是「惰性删除（访问时判定）+ 主动抽样（hz=10 每秒抽样）」；
逻辑上过期即不可见，且**整键删除**（不是删 field、也不是按 Stream 元素裁剪）。

重大风险（已告知用户）：`lgw:cmd:queue` 设 TTL 后若长期空闲，key 连同消费者组 `device-service`
一起消失，而 `RedisCmdWorker.ExecuteAsync` 只在启动时 `EnsureGroupAsync()` 一次 → 之后
`StreamReadGroupAsync` 持续 NOGROUP 报错，命令通道永久卡死需重启，且未 ACK Pending 全丢。
推荐改为 `XTRIM MINID`（StackExchange.Redis 3.0.11 支持）按时间裁剪，key 与消费组保留。

### 已实施：TTL 收敛落地（第 1 项完成）

用户确认只给两个键设 TTL：`lgw:device:{id}:cmd:{seq}`、`lgw:device:{id}:aging:{pn}:history`；
`lgw:cmd:queue` 不设（保持 MAXLEN 裁剪）。

改动：
- 新增 `Bluetti.Device.Redis/RedisTtl.cs`（DefaultDays=7 唯一改动点，含"哪些键禁止设 TTL"的注释清单）。
- `RedisHelper.StreamAddAsync / ObjectToStreamAsync` 新增可选 `ttl` 参数（默认 null 不设过期，写后 KeyExpire）。
- `CommandRepository` 删私有 CommandTtl，改引用 RedisTtl.Command（7 处写入点）。
- `DeviceRepository.SaveAgingDataAsync` 的 aging history 传 ttl（每次采样刷新）。
- `AGENTS.md` 的"关键约定与陷阱"新增 Redis TTL 约定条目；方案文档标注实施状态。
