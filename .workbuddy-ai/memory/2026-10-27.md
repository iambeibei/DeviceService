## start_aging 超时重发（新 Seq）与节点异常判定

**需求**：`start_aging` 下发后 20s 无 `cmd/reply` 即重发，最多 5 次；5 次都无回复则取消下发并标记该节点异常。
设备正常回复形态：`device/{id}/cmd/reply/point` 的 `{"Seq":6,"Data":{"CmdSeq":<下发Seq>,"Code":1,"Msg":"指令重复，老化已启动","CmdData":null}}`。

**用户确认的决策**：
- 5 次无回复但设备已上报 `agingStart` → 不判异常，只标 `timed_out`、保持发送门等终态事件（避免重复启动老化）；
- 异常表达复用现有机制（命令 Hash `failed` + `event:fault` Hash/Stream + publish `event:fault` + 群控剔除）；
- 新增独立配置 `StartAgingReplyTimeoutSeconds=20` / `StartAgingMaxAttempts=5` / `StartAgingRetryDelayMilliseconds=1000`，普通命令仍 15s；
- **每次重发使用新的下发 Seq**（用户选择，与同 Seq 重发方案不同）。

**核心设计（改动前必须理解）**：区分「逻辑 Seq」与「下发 Seq」。
- 逻辑 Seq = Stream Entry 的 Seq，绑定 `cmd:{seq}` 键、`runtime.CurrentAgingSeq`、群控 `RunSeq`、批次 ACK、平台读结果入口，全程不变；
- 下发 Seq：第 1 次复用逻辑 Seq，第 2 次起由 `CommandRepository.NextAttemptSeqAsync()` 从同一个 `lgw:cmd:seq` 计数器新取（**必须复用同一计数器**，否则与未来 Stream Seq 撞号会覆盖命令 Hash）；
- `CurrentAgingSeq` 绝不能写成下发 Seq，否则 `DeviceEventHandler` 的 `CurrentAgingSeq→cmd:{seq}.RecordId` 关联取不到 RecordId、群控 `RunSeq` 对不上批次。

**改动**：
- `CommandRepository` 新增 `NextAttemptSeqAsync` / `UpdateAttemptProgressAsync`（只写 RetryCount+LastAttemptSeq，避免覆盖并发状态）/ `FinalizeAttemptsAsync`（回写逻辑记录，无终态保护但拒绝把 `completed` 降级，用于兜住迟到回复）；
- `CmdInfo` 新增 `LastAttemptSeq`；
- `RedisCmdWorker` 新增 `SendStartAgingWithAttemptsAsync` + `FinalizeStartAgingAttemptsAsync`，`ProcessAgingQueueAsync` 收尾分支改为按 `completed/failed/timed_out + NodeFault` 分流；
- `GroupControlService.HandleStartAgingNoReplyAsync`：写 fault + 从 `run:{seq}:participants` 剔除（`RegisterAgingBatchAsync` 在下发前就登记参与集合，不移除会永久阻塞整架阶段屏障）；
- `GroupControlRunExcludeReasons` 新增 `start_aging_no_reply`（不参与回归，回归只认 `device_offline`）；
- 同步 `CODEBUDDY.md`，新增 `docs/老化指令重发与节点异常判定.md`。

**已知限制**：重试中途重启不会续跑（逻辑记录已是 `timed_out`，恢复分支不重发）；迟到回复只修正 `cmd:{下发Seq}`、逻辑记录保持 `failed`。

**上线前必须实测**：已老化状态下换新 Seq 重发，确认固件仍回 `Code=1 / 指令重复` 且不重启老化（若固件按 CmdSeq 去重则新 Seq 会被当新任务）。

**验证**：`dotnet build DeviceService.slnx` → 0 错误（4 个警告均为原有）。

## 修复：OTA 层内分组被上下线事件打乱，导致本层被误判"全部完成"

**现场日志现象**（架 88，设备 880000001，第 1 层只有它一台）：
1. `OTA 补发第 1 次（第 1 层 1/1 组）… 待完成=1, DeviceIds=880000001`
2. 设备发 `down_line` 掉线 → `MarkOfflineAsync` 把它的 MeshLevel 条目从 `lgw:ota:88:1` 删掉
3. **`OTA 第 1 层处理结束，本层 0 组全部处理完成`** ← 组数变成 0
4. 设备随后 `up_line` 回来，但这一层已经"过完"，再也不会被下发

**根因**：`BuildLevelGroupsAsync` 每次轮询都按**实时** `lgw:ota:{架}:{层}` 清单重算分组。
设备掉线被移出清单 → `targets ∩ 层清单` 变空 → `groups.Count = 0`
→ `CurrentGroupIndex(1) > groups.Count(0)` → `CompleteLevelAsync` 误判完成。

我此前在代码注释里写的假设"层清单由上下线事件维护，OTA 期间不重启，因此快照是稳定的"
是**错的**——掉线/重连随时会发生。

**修复**：层成员快照落库，本层内所有判定都读快照。
- `RedisKeys.OtaBatchLevelMembers(架, seq, 层)` → `lgw:ota:{架}:run:{seq}:level:{层}:members`（Set，TTL=`RedisTtl.OtaBatch`）
- `OtaUpgradeRepository.SetLevelMembersAsync` / `GetLevelMembersAsync`
- `RedisHelper` 新增批量重载 `SetAddAsync(string key, IEnumerable<string> values)`
  （原来只有单值重载，编译报 CS1503）
- `BuildLevelGroupsAsync`：先读快照；为空才按「targets ∩ 实时清单」建立一次并落库，
  之后本层内不再受上下线影响

**修复后的行为**：设备掉线时它仍在快照里且仍是 `pending` → 本组不算完成 →
继续按 `ResendIntervalMinutes`(5min) 补发 → 设备 `up_line` 回来后下一次补发就能到达 →
收到 OTACP 才进下一组。若一直不回来，走本组 30 分钟超时（`AbortOnLevelTimeout=true` 会整批作废）。

**教训**：凡是"每次轮询重算的集合"，都要检查它的上游是否会被并发事件（上下线）修改。
分层 OTA 里层清单就是这样的易变集合，必须快照化。构建 0 错误。
