## 老化门控 / 群控掉线行为排查（只读分析，未改动代码）

回答"子节点掉线会不会被剔除群控、重上线是否回归"。结论要点：

- **群控剔除只在「Mode=2 + 该设备属于当前已激活批次 participants」时发生**
  （`GroupControlService.HandleDeviceOfflineAsync`，由 `DeviceOfflineHandler` 调）。
  批次尚未激活（无 CurrentRunSeq）时掉线不剔除，设备仍留在候选 participants，
  重新上线后上报 agingStart 仍可参与本批。
- **一旦被剔除就本批不回归**：`RecordTaskCompletionAsync` 屏障用 participants 判成员，
  `ActivateRunUnsafeAsync` 要求 participants 含该设备，`RecoverCurrentRunUnsafeAsync`
  在批次 Finished/Cancelled/Conflict 或设备不在 participants 时拒绝恢复。
  `ExcludedRejoinMode` 当前只有 `None`。只能等下一个 start_aging（新 RunSeq）。
- 剔除后若 participants 被清空 → `FinishRunUnsafeAsync` 直接结束批次（否则挂死）。

## 发现的实现缺陷（未修复，待确认）

`AgingCommandGate.TryForceReleaseOfflineAsync` 离线兜底释放**实际无法放行**：
它只把 `gate.Reserved = false`，但没有改 `gate.AgingState`；
而 `WaitAndReserveAsync` 的放行条件是 `!reserved && !IsAgingStart(state)`。
设备 agingStart 中掉线时 AgingState 恒为 "agingStart" → 强制释放后仍被挡住，
每 `AgingCommandGate:OfflineReleaseTimeoutMinutes`（默认 30）重复一次"强制释放"告警，
命令永远发不出去。配套事实：掉线不清 `CurrentAgingSeq`（只有 agingIdle/Stop/Error 才清），
服务重启后 `EnsureInitializedAsync` 也会据此继续 Reserved=true。
修复方向：强制释放时同步把 AgingState 置为非 agingStart（或引入 forcedRelease 标记参与放行判断）。
（本条缺陷本轮未修，用户选择先做回归功能。）

## 已实现：掉线设备限时回归本批次（本轮改动）

需求：网络抖动掉线的子节点，重新上线后应能回到本批次，但要有回归时限（10 分钟）。

设计取舍（重要，后续改动别破坏）：
- **判定点放在 `HandleAgingStateAsync` 的 agingStart 分支，不是 `DeviceOnlineHandler`**。
  用户原方案是上线时读 `runtime.AgingState`，但该字段只在状态上报时更新、掉线不清空，
  上线瞬间读到的是掉线前残留值，条件恒真，区分不出"网络抖动后仍在跑"和"掉电重启任务已丢"。
- **只允许 `Reason=device_offline` 回归**；终态剔除（aging_terminal）和超时剔除（stage_timeout）不回归。
- **阶段对齐**：剔除时记录当时阶段到新键 `lgw:group-control:{n}:run:{seq}:excluded:meta`
  （Hash，field=DeviceId，值=JSON {DeviceId,Reason,Stage,ExcludedAtUtc}）。
  回归时若 `meta.Stage != state.CurrentStage`（全架已推进），把它计入 completed 做本阶段豁免、
  从下一阶段起参与；否则按正常节点等它报 TaskCP。
  原因：`RecordTaskCompletionAsync` 只做 Seq 单调去重、不校验 Seq 属于哪个阶段，
  落后一阶段的设备补报会被误判为当前阶段完成 → 错误放行；不豁免又会永久阻塞。

改动文件：`RedisKeys.cs`（新键）、`Models/GroupControlState.cs`（新增 ExcludedMeta 模型 + ExcludeReasons 常量）、
`GroupControlRepository.cs`（Set/Get/RemoveRunExcludedMeta + RemoveRunExcludedDeviceAsync）、
`GroupControlService.cs`（配置项 + ExcludeParticipantUnsafeAsync 加 stage 参数写 meta + 新增
TryRejoinExcludedParticipantUnsafeAsync）、`appsettings.json`、`AGENTS.md`。

构建：0 个 CS 错误。但 `dotnet build DeviceService.slnx` 报 MSB3027/MSB3021——
服务进程（DeviceService，PID 10048）锁住 `DeviceService\bin\Debug\net10.0\Bluetti.Device.Redis.dll`，
需停止服务后再构建才能完全通过。（后续构建时进程已停止，构建 0 错误通过。）

## 已实现：修复 AgingCommandGate 离线兜底释放失效

缺陷：强制释放只清 `Reserved`，放行条件却还要求 `!IsAgingStart(AgingState)`，
而掉线设备不会再上报终态 → 内存 AgingState 恒为 agingStart → 每 30 分钟重复"强制释放"告警，命令永不放行。

修法（关键取舍，别改回去）：
- **不要**把 `gate.AgingState` 置空/改成非 agingStart 来开门——`GetAgingStateAsync` 的返回值被
  `RedisCmdWorker` 第 367 行用于判断「published + agingStart → 只等原命令回复、不重发」，
  置空会让服务把正在跑的老化命令按原 Seq 重发一遍，风险比阻塞更大。
- 正确做法：给 `DeviceGate` 加 `ForceReleased` 标记，放行条件改为
  `!reserved && (!IsAgingStart(state) || forceReleased)`；占用门时立即清标记 → 只穿透一条，
  不会把排队命令一次全放出去。`NotifyAgingState` / `ReleaseAfterCommandFailureAsync` 里清除标记，
  保证真实状态优先（设备回来仍报 agingStart 时门会重新关上，不打断进行中的老化）。
- 离线判据同时从 `_devices.GetAsync().Online`（runtime 字段，会被 MarkSeenAsync 刷成 true）
  换成 `_devices.IsDeviceOnlineAsync`（`lgw:devices:online` 权威列表），与 `DispatchAsync` 判据一致。

改动文件：`Services/AgingCommandGate.cs`（5 处）、`AGENTS.md`。构建 0 错误。

## 已实现：OTA 批量升级群控（新功能）

需求：一条 `Action=ota` 批量指令 = 一个老化架的升级批次；逐台下发 → ESP32 下载完上报
`device/{id}/event/OTACP` → 完成数 == 下发数 或 超时 10 分钟 → 广播 `server/rack/{架}/CanRestart`
才算允许重启，保证整架升级完整性。

已定设计（用户确认，后续别改偏）：
- 批次键 = **ota 指令 Seq + 架号**（跨架自动拆多批，各自计数各自广播）。
- 上报关联靠**服务端 deviceId→批次映射**：OTACP 报文的 Seq 是设备自身消息序号，
  与 ota 指令 Seq 完全无关（用户给的示例里两者差了一个数量级），所以不能按 Seq 反查批次。
  上报 Data.AgingNumber 只做一致性校验告警，不作为归属依据。
- 下发前查 `lgw:devices:online`，离线设备 MarkFailed 且不计入 dispatched
  （否则批次永远凑不齐只能等超时兜底）。
- 同架已有活跃批次 → 新指令直接 MarkFailed（RejectConcurrentBatchPerRack）。

关键实现细节：
- 下发计数挂在 `ProcessOneCommandAsync` 的 `onPublished` 回调（Publish 成功才计数），
  普通设备队列原本传 null，现在传回调。OTA 命令仍走普通队列、仍会等 15s 回复超时，v1 未改。
- MQTT 已订阅 `device/+/event/+` → OTACP 不需要改订阅；Handler 按接口反射注册，
  新增 `OtaCompletionHandler` 不用动 Program.cs 的路由，只加服务注册。
- 重启 Seq 复用 `lgw:cmd:seq`；发布前写 `state.PendingRestart`，失败保留原 Seq 下轮轮询重试
  （与 CanNextstep 同构）。

新增文件：`Bluetti.Device.Redis/OtaUpgradeRepository.cs`、`Models/OtaBatchState.cs`、
`DeviceService/Services/OtaUpgradeService.cs`、`Handlers/OtaCompletionHandler.cs`。
修改：`RedisKeys.cs`、`RedisTtl.cs`、`MqttTopic.cs`、`RedisCmdWorker.cs`、`Program.cs`、
`appsettings.json`、`AGENTS.md`。构建 0 错误，未做真机验证。

用户补充的业务前提（据此决定 ota 命令 15s 回复超时不用处理）：
**OTA 期间不会下发其它指令**，所以"ota 命令在普通队列里等 15s timed_out、堵住该设备后续命令"
这个副作用在当前业务下不存在，v1 无需给 ota 加"发布即完成"分支。
注意：OTA 重启会让设备掉线（down_line）→ 若此时有群控批次在跑会被按 device_offline 剔除；
重启通常在 1 分钟内，落在 `ExcludedRejoinTimeoutMinutes`（10）内，重新上报 agingStart 可回归本批。
