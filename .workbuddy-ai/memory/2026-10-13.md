## 项目架构通读（只读分析，未改动任何代码）

完整阅读了两个项目的全部源码与配置，产出架构梳理（模块划分 + 三条数据流 + 设计取舍）。

读代码时发现的、文档(AGENTS.md / CLAUDE.md) 与代码不一致或有风险的点，供后续参考：

1. **协议文档过时（重要）**：`AGENTS.md` 与 `CLAUDE.md` 都写明下行 MQTT payload "只有 {Seq, Data}，RecordId 不下发给 ESP32"，
   但 `RedisCmdWorker.PublishCommandAsync()` 实际还带了第三个字段 `["RecordId"]`。若固件端按文档解析，需确认是否兼容。
2. **单实例假设**：`AgingCommandGate._gates` 与 `GroupControlService._states` 都是进程内内存状态 + 进程内锁，
   多实例部署会状态分裂（docs 文档 §2.8 已记录，未处理）。
3. **`AgingDataHandler` 在 MQTT 处理线程内同步 HTTP POST**（`DataSQLHelper.JsonHttpPostAsync`），
   与 `AgingRecordCallbackClient` 的"异步入队、后台串行发"是两套不同做法；前者在 API 慢时会拖慢消息路由。
4. **`DataSQLHelper` 静态 HttpClient 全局忽略 SSL 证书**（`ServerCertificateCustomValidationCallback` 恒 true），
   与 `AgingCallback` 段的可配置项不同，无开关。
5. **时间戳混用**：`DeviceEventHandler` / `PublishFaultAsync` 等处 `ReceivedAtUtc` 实际写的是 `DateTime.Now`（本地时间）。
6. 无测试项目、无 CI，验证手段仅 `dotnet build DeviceService.slnx` 为 0 错误。

## 群控阶段放行倒计时排查（只读分析，未改动代码）

现象：Completed=1 / Participants=4 / Threshold=2 却打印"完成数已达半数"并起表；放行疑似超时触发。

结论要点（复用于后续同类排查）：
- **两条放行路径最终汇入同一段代码**：`EvaluateNextStepUnsafeAsync` 先跑 `ExpireStageTimeoutUnsafeAsync`（剔除未完成者），
  再重新读 participants 判 `canRelease`。超时剔除后 participants 变小 → `canRelease` 变 true → 走的和"正常全员完成"
  **完全相同的放行分支**，因此仅看"创建阶段放行指令 / 已按老化架主题放行"两条日志无法区分触发来源。
- **阈值算术没有错**：`ComputeHalfThreshold(4)` = Ceil(4/2.0) = 2，比较写法 `completed.Count >= threshold` 也正确。
  真正原因是 `GroupControl:StageTimeoutRequireHalf=false`（代码默认 false，appsettings.json 也显式写 false）
  把该比较 `||` 短路掉了，起表条件实际只剩 `completed.Count > 0`；而第 1130 行的日志文案仍写"已达半数" → 纯文案误导。
- **`LastStageTimeoutSeq` 不是可靠判据**：`ExpireStageTimeoutUnsafeAsync` 第 1381-1382 行无条件写它，
  即使 `expired.Length == 0`（"到期但已全部完成"分支）也会写。可靠判据是 Redis
  `lgw:group-control:{n}:run:{seq}:excluded` 是否非空、以及 `event:fault`（Reason=stage_timeout）。
- **`StageTimeoutMinutes` 只在启动时读一次**（构造函数第 91 行，`?? 10` 是硬编码兜底），
  且已落库的 `StageDeadlineUtc` 是绝对时刻 → 改成 5 分钟后必须重启，且重启前已起表的架仍按旧 10 分钟到期。
  其它可覆盖该值的来源：user-secrets（csproj 有 UserSecretsId）、环境变量 `GroupControl__StageTimeoutMinutes`。
  `appsettings.Development.json` 无 GroupControl 段，不构成覆盖。
- 故障 payload（`BuildGroupControlFaultPayload`）相较设计文档 §7.1 少了 Stage / TimeoutMinutes /
  CompletedCount / ParticipantCount 字段，排障时拿不到上下文。
