# 老化指令（start_aging）重发与节点异常判定

## 背景

ESP32 收到 `server/{deviceId}/cmd/start_aging` 后会立即回复
`device/{deviceId}/cmd/reply/point`：

```json
{"Seq":6,"Data":{"CmdSeq":123213213,"Code":1,"Msg":"指令重复，老化已启动","CmdData":null}}
```

- `Seq`：设备侧消息序号，与命令无关；
- `Data.CmdSeq`：下发时的命令 `Seq`，是唯一的回复匹配键；
- `Data.Code`：`1` = 成功（含"指令重复，老化已启动"这类幂等回复），其它 = 失败；
- `Data.Msg`：只落库留痕，不参与判定。

改造前 `start_aging` 是**一次性下发**：20s（旧为 15s）内没等到回复就标 `timed_out`，
并且 `timed_out` 不释放老化发送门 —— 该设备后续所有 `start_aging` 会一直排队，
只能靠 30 分钟离线兜底（`AgingCommandGate:OfflineReleaseTimeoutMinutes`）才能放行一条。

## 改造后的行为

| 参数 | 默认值 | 说明 |
|---|---|---|
| `CommandProcessing:StartAgingReplyTimeoutSeconds` | 20 | 单次等待回复超时 |
| `CommandProcessing:StartAgingMaxAttempts` | 5 | 总下发次数（含首次），`1` = 不重发 |
| `CommandProcessing:StartAgingRetryDelayMilliseconds` | 1000 | 两次下发间隔，`0` = 不间隔 |

最坏耗时 = 5 × 20s + 4 × 1s ≈ 104s。

### 时序

```
占发送门 → 第 1 次下发(Seq = 逻辑 Seq) → 等 20s
   ├─ 有回复 → 结束
   └─ 超时 → 第 2 次下发(Seq = 新分配) → 等 20s
              └─ … 最多 5 次 …
                    ├─ 仍无回复 且 设备未上报 agingStart → 判节点异常
                    └─ 仍无回复 但 设备已上报 agingStart → 只标 timed_out，保持门
```

### 结果分支

| 最终状态 | 发送门 | 其它动作 |
|---|---|---|
| `completed`（`Code == 1`） | 保持关闭，等 `agingIdle/Stop/Error` | 打 Info，含 `Code` / `Msg` / 当前 `AgingState` |
| `failed`（设备明确回 `Code != 1`） | 释放（`AgingState` 为 `agingStart` 时除外） | 清 `CurrentAgingSeq`（同上例外） |
| `failed`（5 次都无回复，判节点异常） | 释放 | 清 `CurrentAgingSeq`、写 `event:fault`、剔除群控参与集合 |
| `timed_out`（5 次无回复但已 `agingStart`） | **保持关闭** | 打 Warning，等终态事件 |

## Seq 的两种身份（最容易改错的地方）

- **逻辑 Seq**：Redis Stream Entry 里那条 `Seq`。它同时是
  `lgw:device:{id}:cmd:{seq}` 的键、`runtime.CurrentAgingSeq`、群控 `RunSeq`、
  批次 ACK 的 key，以及平台读取命令结果的入口。**全程不变**。
- **下发 Seq**：只有第 1 次复用逻辑 Seq；第 2 次起由 `CommandRepository.NextAttemptSeqAsync()`
  从同一个 `lgw:cmd:seq` 计数器新取。仅用于 MQTT 报文的 `Seq` 和 `Data.CmdSeq` 回复匹配，
  每次尝试单独落一条 `cmd:{下发Seq}` 便于追溯。

`CurrentAgingSeq` **绝不能**写成下发 Seq：`DeviceEventHandler` 用
`CurrentAgingSeq → cmd:{seq}.RecordId` 关联业务回调，群控用 `CurrentAgingSeq` 当 `RunSeq`
匹配批次，写错会导致回调拿不到 `RecordId`、群控批次无法激活。

多次尝试结束后由 `CommandRepository.FinalizeAttemptsAsync` 把最终结果回写到逻辑记录。
该方法刻意**不做终态保护**（耗尽时逻辑记录已是 `timed_out`，必须能改成 `failed`），
但**不会把 `completed` 降级** —— 用来兜住"更早某次尝试的迟到回复已经落库"的场景。

## 节点异常的表达

判定节点异常时写三处（均为项目已有机制）：

1. `lgw:device:{id}:cmd:{逻辑Seq}` → `Status=failed`，
   `ResultMessage` 含全部 5 个下发 Seq 与超时值；
2. `lgw:device:{id}:event:fault`（最新值 Hash + 历史 Stream），
   载荷 `Reason=start_aging_no_reply`；
3. Redis Pub/Sub `event:fault`，供订阅方实时告警。

同时 `GroupControlService.HandleStartAgingNoReplyAsync` 会把该设备从当前 `mode=2`
批次的 `run:{seq}:participants` 中剔除（`Reason=start_aging_no_reply`，**不参与本批次回归**）。
这一步是必须的：`RegisterAgingBatchAsync` 在下发前就登记了参与集合，失败设备若不移除，
批次激活后会永久阻塞整架阶段放行屏障。

## 已知限制

1. **重试中途重启**：逻辑记录此时是 `timed_out`（终态），重启后的 Pending 恢复分支不会续跑重试，
   发送门要等 30 分钟离线兜底才释放。`RetryCount` / `LastAttemptSeq` 已落库，
   后续可基于它们做"重启后续跑"。
2. **迟到回复只修正尝试记录**：若某次尝试的回复在最终判定之后才到达，
   `cmd:{下发Seq}` 会被修正，但逻辑记录保持 `failed`，两者不一致。属审计信息，不影响调度。
3. **新 Seq 的固件前提**：若固件按 `CmdSeq` 去重，新 Seq 会被当成全新任务。
   当前观测到的回复是"指令重复，老化已启动"，说明是按内容去重，新 Seq 安全。
   **上线前需实测**：在已老化状态下换新 Seq 重发，确认仍回 `Code=1 / 指令重复` 且不重启老化。
4. `lgw:cmd:seq` 被尝试 Seq 占用后，计数器里不是每个 Seq 都有对应 Stream Entry，
   排查时不要假设一一对应。
